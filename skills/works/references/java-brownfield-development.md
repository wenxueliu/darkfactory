# Java 存量开发

## API 复用与分层

### 层级定义

- `T0`：目标类自身已经存在且可直接调用的方法。普通内部复用使用直接方法调用；若正确性依赖 Spring 代理增强，不得把 `this` 自调用当作有效复用。
- `T1`：同一业务层、同一模块或明确允许依赖模块中的已有公开 Service API。
- `T2`：项目架构明确允许的跨层或跨模块公开端口。Mapper/Repository 仅在目标 Service 本就拥有该聚合的持久化职责时允许进入 T2；不得把它当作找不到 Service API 时的通用 fallback。

### 逐层决策算法

对 requirement.md 的每个功能点分别执行，不能跨功能点共用一个结论：

1. 从 `T0` 开始，记录本层搜索范围并枚举全部相关候选。
2. 对每个候选执行下面的全部硬门禁，任一门禁失败就拒绝，并记录代码位置与原因。
3. 当前层存在通过全部门禁的候选时，只在这些合格候选中按契约匹配度和已有调用约定排序，选定一个并停止；不得继续搜索 T1/T2 后改选更低层候选。
4. 当前层没有合格候选时，必须证明候选为空或所有候选均被拒绝，才能依次降级到下一层。
5. 仅当 T0、T1、T2 全部穷尽后，才允许 `selected` 为 `null` 并提供最小新增实现的 `fallback`。不得复制已有 API 实现后改写，也不得把复制代码称为复用。

硬门禁全部为必选项：

- `semantic_match`：业务语义、前置条件与后置条件和目标行为兼容。
- `callable`：可见性、参数、返回值、泛型与空值约定允许真实调用。
- `no_recursion`：不会直接或间接递归回目标方法。
- `dependency_direction`：不会产生循环依赖、反向依赖或绕过项目既有分层。
- `proxy_safe`：事务、缓存、异步、鉴权等代理增强不会因内部调用失效。
- `transaction_compatible`：传播级别、只读属性、锁与回滚语义兼容。
- `contract_compatible`：异常、错误码、统一响应、幂等性及其他副作用兼容。

已有调用点是确认调用约定的强证据，但不是 API 合法性的必要条件；没有调用点时必须以声明、实现和测试证明门禁。最终实现必须修改已定位的存量入口并保留公开方法签名、既有调用方语义、分层结构和代码风格。新增辅助类不能代替存量修改；只有 `reuse_decisions` 明确批准 fallback 时才能新增生产入口或实现。

### 结构化决策

严格按 `next_action.check` 中的固定 JSON schema 提交 `reuse_decisions`，其中 `current_class`、`same_layer`、`cross_layer` 分别对应 T0、T1、T2。每个候选的 `gates` 必须完整包含上述七个布尔字段，`feasible` 必须等于七项全部为 `true`；任何门禁失败时把失败项写入非空 `reject_reasons`，可行候选必须 `reject_reasons=[]`。选择 T1/T2 时，不得存在更高优先层的可行候选；`selected=null` 只表示三个层级的候选全部不可行，并批准实现最小新增 fallback。`search_evidence` 只要求已经到达的层级：选择 T0 只要求 T0，选择 T1 要求 T0/T1，选择 T2 或 fallback 要求三层；选定后立即停止，不能伪造低优先层搜索。JSON 之外不要附加说明。

实现步骤必须按 `next_action.check` 提交 `implementation_reuse` JSON。`selected` 非空时对应项必须为 `action=invoke`、`symbol` 与选定值完全一致；`selected=null` 时必须为 `action=fallback`、`symbol=null`。`call_site` 始终填写实际代码的 `path:line`。

## 测试先行

在修改生产代码之前为每个功能点编写或调整单元测试：

1. 优先沿用项目已有的 JUnit 版本、扩展和断言库；项目已使用 JUnit 时不得另引入测试框架。
2. 测试必须直接覆盖 requirement.md 的功能行为、边界条件和明确的兼容性要求。
3. 优先扩展最接近目标类的已有测试类；只有职责清晰且没有合适测试类时才新增测试类。
4. 隔离外部系统只使用项目已有的 mock、stub 或 test fixture 方式；不要把单元测试升级成依赖数据库、网络或完整容器的集成测试。
5. 先运行新增或修改的相关测试，确认它因尚未实现的目标行为而失败。编译错误、依赖缺失、环境错误或无关断言失败不算有效红灯。
6. 不得为了通过测试而删除断言、跳过测试、吞异常或降低验收标准。

若项目明确采用非 JUnit 测试框架且引入 JUnit 会破坏既有构建约定，沿用现有框架，并在检查证据中说明判断依据。
